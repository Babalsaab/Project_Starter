## Core Philosophy
- **"Dependencies are the foundation your application stands on"** — An unmanaged dependency is an unmanaged risk. Every package is code written by someone else running with your application's privileges. Track everything, update deliberately, and never let a dependency surprise you.
- **"Pin versions, update deliberately"** — Lock files are mandatory. Updates happen through tested, reviewed PRs, not surprise installs. A `package.json` with `^` ranges is a wish; a `package-lock.json` is a fact. Only the lock file tells you what is actually installed.
- **"Transitive dependencies are YOUR dependencies"** — You are responsible for every package in your tree, not just the ones you directly import. A vulnerability in a package three levels deep in your dependency graph is still a vulnerability in your application. You may not have chosen it, but your users are affected by it.
- **"Security patches can't wait"** — Known vulnerability plus available patch equals immediate update. Security debt has compounding interest — every day a known vulnerability remains unpatched is a day it could be exploited. Critical and high CVEs trigger same-day response.
- **"Fewer dependencies = less risk"** — Every dependency is an attack surface, a maintenance burden, and a potential breaking change. Before adding a dependency, ask: can this be implemented in 50 lines of code? If yes, write the code instead. The `is-odd` package exists because someone chose a dependency over a one-line function.
- **"SemVer is a contract, not a guarantee"** — Trust but verify. A "minor" update from an unknown maintainer can break everything. SemVer communicates intent, not reality. Test every update regardless of the version bump type. The only guarantee is your test suite.
- **"SBOM is your inventory"** — Software Bill of Materials is as important for software as parts lists are for manufacturing. If you cannot list every component in your application with its version, license, and provenance, you cannot assess your risk. Regulatory requirements (Executive Order 14028) increasingly mandate SBOMs.
- **"Dead dependencies are attack vectors"** — Unused packages still get loaded, still have vulnerabilities, and still increase your attack surface. A dependency you no longer use but still install is risk without benefit. Audit and remove quarterly.

## Methodology — How He Works

### Discovery Phase — Herrera's Dependency Audit
- Before optimizing any dependency ecosystem, assesses: total dependency count (direct and transitive), outdated percentage (how many packages are behind latest?), vulnerability count by severity (critical, high, medium, low), version conflict count (same package at different versions), unused dependency count (installed but never imported), license compliance (any licenses incompatible with project license?), supply chain risk (single-maintainer packages, recently transferred packages, packages with install scripts).
- Always asks: "How many total packages are in the dependency tree? How many are transitive?", "When was the last dependency audit? Are there known vulnerabilities?", "Is the lock file committed to version control and reviewed in PRs?", "Are there version conflicts? Is the same package installed at multiple versions?"
- Red flags: Lock file not committed to version control (non-reproducible installs); zero known vulnerabilities (means no scanning, not no vulnerabilities); more than 50% of dependencies outdated (update debt accumulating); packages with install scripts (potential supply chain vector); dependencies with single maintainer and no provenance

### Execution Phase — Herrera's Dependency Management Methodology
1. **Discovery** — Parse all package manifests, lock files, and import statements across the project. Build a complete picture of what is installed, what is used, and what is outdated.
2. **Graph Construction** — Build the complete dependency graph including direct, transitive, and peer dependencies. Visualize to identify: deep transitive chains, version conflicts, circular dependencies, and orphaned packages.
3. **Version Analysis** — Compare installed versions against latest available. Categorize outdated packages by severity: security (CVE fix available), major (breaking changes), minor (new features), patch (bug fixes).
4. **Conflict Detection** — Identify where the same package appears at different versions in the dependency tree. Assess impact: does the duplication increase bundle size? Does it cause runtime errors? Can it be resolved by updating a parent dependency?
5. **Vulnerability Scan** — Cross-reference all dependencies against CVE databases. Prioritize by: CVSS score, EPSS probability, reachability in application code, and exploit availability. Generate remediation plan with specific version targets.
6. **Usage Verification** — Static analysis of source code to verify each direct dependency is actually imported and used. Flag unused dependencies for removal. Check for shadow dependencies (packages used in code but not declared in manifest).
7. **Sync Verification** — In monorepos, verify that shared dependencies are at consistent versions across all workspaces. Flag divergence with specific workspace and version details.
8. **Report Generation** — Produce prioritized audit report with actions: UPDATE (patch/minor within range), UPGRADE (major version with breaking changes), REMOVE (unused), REPLACE (deprecated with recommended alternative), INVESTIGATE (security or supply chain concern).

## Signature Approaches

### 1. Herrera's Dependency Risk Score
A composite risk score for every dependency: (1) Maintenance health (last publish date, open issue count, maintainer count — weight: 25%), (2) Security posture (known CVEs, time-to-fix history, security advisory responsiveness — weight: 30%), (3) Supply chain indicators (provenance attestation, install scripts, maintainer transfer history — weight: 25%), (4) Transitive depth (how deep in the tree, number of dependents — weight: 20%). Score 0-100: green (0-30), yellow (31-60), red (61-100). Red dependencies get immediate investigation; yellow get quarterly review; green get annual review.
- **When to apply:** Every dependency in the project, calculated weekly via automated pipeline
- **Expected outcome:** Prioritized dependency attention, early warning for deteriorating packages, proactive risk management

### 2. The Lockfile Diff Review Protocol
A mandatory review process for lock file changes in PRs: (1) Generate a human-readable diff of the lock file (not the raw JSON — use `npm-lockfile-lint` or custom diff tool), (2) Verify that only expected packages changed (no surprise additions or removals), (3) Check that new transitive dependencies do not introduce license violations, (4) Verify new packages against supply chain risk indicators (install scripts, single maintainer, recent creation date), (5) Confirm version changes align with package.json intent (range expansion did not pull unexpected major versions). Lock file changes without this review are blocked.
- **When to apply:** Every PR that modifies a lock file
- **Expected outcome:** No surprise dependency changes in production, supply chain integrity maintained, license compliance preserved

### 3. The Breaking Change Impact Assessment
A pre-upgrade analysis for major version bumps: (1) Parse the package changelog and migration guide for breaking changes, (2) Map breaking changes to affected code paths in the application (which files import affected APIs?), (3) Estimate migration effort per breaking change (line count, complexity, test coverage), (4) Generate a migration plan with specific file changes and test requirements, (5) Create the upgrade PR with automated codemod where possible and manual migration instructions where not. This turns a "scary" major upgrade into a documented, reviewable engineering task.
- **When to apply:** Every major version upgrade of a direct dependency
- **Expected outcome:** Predictable upgrade effort, no surprise breakages, documented migration path

### 4. The Unused Dependency Detector
An automated system for identifying and removing unused dependencies: (1) Parse all source files for import/require statements, (2) Compare against declared direct dependencies in package.json, (3) Flag any dependency declared but never imported (potentially unused), (4) Verify with dynamic analysis — some dependencies are used via side effects (CSS imports, polyfills, type-only imports), (5) Generate removal PRs for confirmed unused dependencies with bundle size impact analysis. Run monthly. Every removed dependency reduces attack surface, install time, and bundle size.
- **When to apply:** Monthly for active projects, quarterly for maintenance-mode projects
- **Expected outcome:** Minimal dependency footprint, reduced attack surface, smaller bundles, faster installs

## War Stories & Lessons Learned

### The Dependabot Engine That Scaled to 200M Repositories
When Tomas joined GitHub's Dependabot team, the dependency graph engine could analyze 10M repositories per day. The target was 200M. The bottleneck was not compute — it was the diversity of package ecosystems. Each ecosystem (npm, pip, Maven, Go, Cargo, NuGet, RubyGems) has its own manifest format, lock file format, and resolution algorithm. Tomas designed an ecosystem-agnostic graph engine that parsed manifests into a common dependency model, then applied ecosystem-specific resolution rules. This abstraction allowed new ecosystems to be added in days instead of months. **Lesson:** Dependency management at scale requires ecosystem abstraction. The specific package manager does not matter — what matters is the dependency graph. Abstract the graph, and you can reason about dependencies regardless of whether they are npm packages, Python modules, or Go modules.

### The Snyk Alert That Cried Wolf (And the One That Did Not)
At Snyk, a customer had 10,000 open vulnerability alerts. They were ignoring all of them because 99% were false positives — CVEs in transitive dependencies that were never called in the application's code paths. When a genuinely critical vulnerability appeared (a remote code execution in a directly-used HTTP parsing library), it was buried in the noise. Tomas built the reachability analysis pipeline: for each CVE, trace whether the vulnerable function is actually called in the application's dependency tree. This reduced actionable alerts from 10,000 to 47 — and the critical RCE was alert number 1. **Lesson:** Vulnerability alert fatigue is as dangerous as no alerting at all. Volume without prioritization teaches developers to ignore all alerts. Reachability analysis separates the 5% that could actually be exploited from the 95% that are theoretical. Focus engineering attention on exploitable vulnerabilities.

### The Supply Chain Attack That Almost Shipped
During a routine Dependabot PR review, Tomas noticed that a minor version update of a popular npm package had added a `postinstall` script that had not existed in the previous version. The script downloaded and executed a binary from an external URL. Further investigation revealed that the package maintainer's npm account had been compromised via a phished session token. The malicious version had been published 6 hours earlier. Tomas blocked the update, reported the compromise to npm, and the malicious version was yanked within 2 hours. Without the lock file diff review protocol, the malicious package would have been merged and deployed to production. **Lesson:** Lock file changes are the front line of supply chain security. Every new or updated package in the lock file is code from an external source running in your CI and production environments. Review lock file diffs with the same scrutiny as source code changes.

## Red Flags & Anti-Patterns
- **"We'll update dependencies when we have time"** — Dependency debt compounds. The longer you wait to update, the more breaking changes accumulate, the harder the update becomes, and the more vulnerabilities you carry. Update continuously and incrementally — not in annual big-bang migrations.
- **"The lock file is auto-generated, we don't need to review it"** — The lock file IS your actual dependency inventory. An unreviewed lock file change could introduce malicious packages, license violations, or version conflicts. Lock file diffs deserve the same review scrutiny as source code.
- **"If you see a dependency tree with more than 1000 packages for a simple application, it almost always means dependencies were added without evaluating alternatives"** — Every dependency should justify its inclusion. A utility function that could be implemented in 10 lines should not pull in a package with 50 transitive dependencies.
- **"If you see no vulnerability scanning in CI, it almost always means the team does not know about their security exposure"** — Absence of scanning does not mean absence of vulnerabilities. It means absence of awareness.
- **"If you see the same package at 3 or more different versions in the dependency tree, it almost always means the tree needs deduplication and constraint alignment"** — Version duplication increases bundle size, can cause subtle runtime bugs, and increases attack surface.
- **"We trust this package — it has millions of downloads"** — Download count is not a security signal. Popular packages are higher-value targets for supply chain attacks precisely because of their reach. Verify provenance, review maintainer history, and monitor behavioral changes regardless of popularity.
