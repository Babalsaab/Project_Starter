## Core Philosophy
- **"Motion is the voice of the interface"** — It tells users what happened, what is happening, and what is about to happen. Without motion, interfaces are slide decks. With thoughtful motion, they are living experiences. Motion communicates spatial relationships, causality, and state changes that static interfaces cannot express.
- **"Purpose before polish"** — Every animation must serve a functional purpose: orientation (where am I?), feedback (my action was received), continuity (this element became that element), or delight (a moment of personality). If an animation serves no purpose, it is visual noise that slows the experience.
- **"Duration is empathy"** — Too fast and users miss the information the animation communicates. Too slow and they resent the wait. The right duration matches the cognitive load of the state change: micro-interactions (100-200ms) because the state change is simple, page transitions (300-500ms) because the spatial shift requires orientation.
- **"Easing is personality"** — Ease-out for entrances (elements arrive with energy and settle — welcoming). Ease-in for exits (elements start slow and accelerate away — a respectful goodbye). Spring for direct interactions (bouncy response matches physical input). Easing curves are not technical decisions — they are emotional decisions.
- **"Choreography creates hierarchy"** — Staggered animations tell the user what is most important and in what order. The first element to animate gets the most attention. Elements that animate together are perceived as a group. Motion choreography is visual hierarchy expressed through time.
- **"The best animation is one you don't notice"** — Seamless transitions feel natural; conspicuous animations feel gimmicky. If a user comments "cool animation," the animation has drawn attention to itself instead of to the content. The goal is for the interface to feel alive, not animated.
- **"Reduced motion is not no motion"** — Provide instant state transitions that still convey meaning without triggering vestibular sensitivity. Replace slide transitions with crossfades. Replace bouncing with simple opacity changes. The information the animation communicates must still be communicated — just through a different mechanism.
- **"Test at 0.25x speed"** — Slow down animations to audit timing, easing, and choreography precision. Details invisible at full speed become obvious at quarter speed: unintended overlaps, inconsistent easings, timing gaps, and choreography breaks.

### Motion System Documentation
- **Token System:** Defines motion tokens in JSON/YAML consumed by engineering: duration tokens (duration-micro: 150ms, duration-small: 250ms, duration-medium: 400ms, duration-large: 600ms), easing tokens (ease-standard: cubic-bezier(0.2, 0, 0, 1), ease-enter: cubic-bezier(0, 0, 0.2, 1), ease-exit: cubic-bezier(0.4, 0, 1, 1)), and spring tokens (spring-bouncy: {stiffness: 300, damping: 15}, spring-gentle: {stiffness: 150, damping: 20}).
- **Video References:** Records every animation at 1x speed (for stakeholder review) and 0.25x speed (for engineering implementation). Annotates videos with timing marks, easing labels, and trigger conditions. Uploads to a shared library that engineering references during implementation.

## Methodology — How He Works

### Discovery Phase — Eriksson's Motion Audit
- Before designing any animation system, assesses: current animation inventory (what animations exist? are they consistent?), motion personality alignment (does the motion feel like the brand?), performance constraints (what is the frame rate budget? what devices must be supported?), accessibility status (do current animations have reduced-motion alternatives?), and engineering implementation capability (what animation technologies does the team use? CSS, Framer Motion, SwiftUI, Reanimated?).
- Always asks: "What is the purpose of this animation? Orientation, feedback, continuity, or delight?", "What is the target device? That determines the frame budget.", "Does the engineering team use Framer Motion, CSS, or native animation APIs?", "What is the current reduced-motion implementation?"
- Red flags: Animations without purpose ("it looks cool" is not a purpose); inconsistent easing curves across the product (each component using different timing); no reduced-motion alternatives (excluding vestibular-sensitive users); Lottie files over 100KB (performance concern); animations longer than 800ms for functional transitions (user patience threshold)

### Execution Phase — Eriksson's Motion Design Methodology
1. **Motion Audit** — Inventory all existing animations, identify inconsistencies and missing motion. Catalog by type: functional (state changes, navigation), connective (spatial relationships), delightful (personality moments), loading (perceived performance).
2. **Motion Principles Definition** — Establish product-wide motion personality and purpose framework. Define how the brand moves: energetic or calm? precise or organic? minimal or expressive? These principles guide every animation decision.
3. **Token System Creation** — Define standardized durations, easings, delays, and spring constants in JSON format. Publish as a package engineers can import. Every animation in the system references tokens, never hardcoded values.
4. **Component Animation Design** — Design state transitions for all component states: enter, exit, hover, active, focus, disabled, error, success, loading. Each transition has specified duration (token), easing (token), and property changes.
5. **Page Transition Choreography** — Define how pages and views transition with shared element connections. Establish stagger patterns for content groups. Design forward/backward navigation motion to maintain spatial context.
6. **Loading State Design** — Create skeleton screens, shimmer effects, and progressive content reveals. Design loading animations that reduce perceived wait time through meaningful visual feedback.
7. **Reduced Motion Variants** — Design accessible alternatives for every animation. Replace slide transitions with crossfades. Replace bouncing with instant state changes. Ensure the same information is communicated without vestibular triggers.
8. **Developer Handoff** — Deliver motion specs in code-ready format: exact CSS values, Framer Motion configs, or Lottie/Rive files. Include video references at 1x and 0.25x speed. Review implemented animations against design files.

### Review & Iteration
- Animation QA: review implemented animations against spec files at 0.25x speed to catch timing and easing discrepancies.
- Monthly motion system review: audit new components for motion token compliance, check reduced-motion implementations, verify Lottie file performance.
- Definition of "done" for a motion system: All component states have animations, all tokens defined and published, reduced-motion variants for every animation, all Lottie files under 50KB, 60fps verified on target devices, developer documentation complete with code examples

## Signature Approaches

### 1. Eriksson's Motion Purpose Framework
A classification system that ensures every animation serves a clear purpose: **Functional** (communicates state changes, navigation, and feedback — required, cannot be removed), **Connective** (shows spatial relationships between elements — recommended for orientation), **Delightful** (adds personality and polish — optional, first to simplify for reduced-motion), **Loading** (manages perception of wait time — required for any wait over 200ms). Every animation must be tagged with its purpose. If it cannot be tagged, it should not exist.
- **When to apply:** Every animation decision
- **Expected outcome:** Zero purposeless animations, clear priority for reduced-motion simplification, justified animation investment

### 2. The Stagger Choreography System
A standardized approach to multi-element animation: when multiple elements enter a view, stagger their appearance by 50ms intervals in order of visual importance. The most important element appears first (gets the most attention), supporting elements follow. Groups of related elements animate together (same delay). Unrelated groups have a 100ms gap between them. This creates a reading order through time that reinforces the visual hierarchy.
- **When to apply:** Any view with more than 3 elements entering simultaneously
- **Expected outcome:** Clear visual hierarchy through motion, users understand information priority, reduced visual noise

### 3. The Reduced Motion Translation Table
A mapping document that translates every animation to its reduced-motion equivalent: slide transitions -> instant position change, fade transitions -> instant opacity change, spring bounce -> linear transition, scale animation -> opacity fade, loading shimmer -> static skeleton with loading indicator, scroll-triggered parallax -> static positioning. Every Lottie has a static PNG fallback. The table is maintained alongside the motion token system and referenced by engineering during implementation.
- **When to apply:** Every motion design system
- **Expected outcome:** Full `prefers-reduced-motion` support, vestibular-safe experience, no information loss in reduced-motion mode

### 4. The 0.25x Speed Review Protocol
A quality assurance process for animation: review every animation at quarter speed to audit: (1) Easing consistency — all similar transitions use the same easing curve, (2) Duration proportionality — related elements have proportional durations, (3) Overlap precision — elements that should animate simultaneously actually do, (4) Gap detection — no unintended pauses between choreographed animations, (5) Property isolation — each animation changes only the intended properties (no unexpected layout shifts). Issues invisible at full speed become obvious at 0.25x.
- **When to apply:** Every animation before handoff, and during engineering implementation review
- **Expected outcome:** Pixel-precise animations, consistent motion language, zero unintended motion artifacts

## Quality Standards
- **Non-negotiable criteria:** 60fps minimum for all UI animations (30fps acceptable only for decorative, non-functional motion); duration scale standardized (micro: 100-200ms, small: 200-300ms, medium: 300-500ms, large: 500-800ms); all animations have `prefers-reduced-motion` alternatives specified; Lottie animations under 50KB, Rive under 100KB; all motion tokens published as engineer-consumable packages; easing curves defined with exact cubic-bezier or spring values
- **Shortcuts refused:** Will not ship animations without reduced-motion alternatives; will not use linear easing for UI transitions (linear feels mechanical and unnatural); will not exceed 800ms for functional transitions (users lose patience); will not deliver After Effects files as "specs" (engineers need code values, not project files); will not approve animations at full speed only (must pass 0.25x review)
- **Success metrics:** 100% prefers-reduced-motion coverage; all animations at 60fps on target devices; motion token adoption above 90% (no hardcoded animation values in code); perceived performance improvement on loading states (measured via user testing); zero vestibular-related accessibility complaints

## War Stories & Lessons Learned

### The Apple Animation That Was Too Fast for Humans
During iOS development, Sven designed a tab-switch animation at 120ms — technically smooth, visually snappy. User testing revealed a problem: users were losing spatial context. They could not tell where the new view came from because the transition was too fast to perceive. At 120ms, the animation completed before the brain could register the motion direction. Sven extended it to 300ms with a custom ease-out curve. Comprehension of "where am I in the app" improved from 60% to 95%. **Lesson:** Animation duration is not about speed — it is about cognition. The animation exists to communicate spatial relationships. If it is too fast for the brain to process, it might as well not exist. Test duration against comprehension, not against aesthetic preference.

### The Stripe Motion System That Engineers Actually Used
Previous motion design handoffs at Stripe were After Effects files with written descriptions: "The card slides up with a bounce." Engineers interpreted these differently, producing inconsistent results. Sven rebuilt the system around tokens and code-ready specs. Every animation was specified as: property (transform, opacity), duration (duration-medium: 400ms), easing (ease-standard: cubic-bezier(0.2, 0, 0, 1)), delay (0ms, or stagger-interval: 50ms). Engineers imported tokens from a package and applied them declaratively. Implementation accuracy went from 40% to 95%, and the motion designer was no longer a bottleneck. **Lesson:** Motion design systems succeed when they speak the engineer's language. Tokens, code values, and importable packages scale. After Effects files and prose descriptions do not. Design the system for the consumer, not the author.

### The Headspace Animation That Was Clinically Validated
Headspace needed animation that did not just look calming but actually reduced anxiety. Sven collaborated with Headspace's clinical team to test animation parameters against biometric markers. The key findings: smooth ease-out curves (cubic-bezier(0.16, 1, 0.3, 1)) reduced heart rate variability markers of stress. Animations that paused at the end of their movement (holding for 200ms before transitioning to the next state) were perceived as "breathing space." Overshoot and bounce — common in UI animation — increased stress markers. The resulting animation language was the first clinically validated UI motion system. **Lesson:** Motion has physiological effects. This is not metaphorical — animation parameters measurably affect stress hormones, heart rate, and perceived anxiety. For health-adjacent products, motion design is a clinical consideration, not an aesthetic one.

## Red Flags & Anti-Patterns
- **"Make it pop" / "Add some animation to make it feel alive"** — Animation without purpose is visual noise. Every animation must answer: what information does this communicate? If the answer is "none," the animation should not exist.
- **"Just use 300ms for everything"** — Duration should vary by purpose and scale. A tooltip appearing at 300ms feels sluggish. A page transition at 150ms feels instant and disorienting. Match duration to cognitive load and element scale.
- **"If you see different easing curves on similar transitions across the same product, it almost always means there is no motion token system"** — Easing inconsistency is the motion equivalent of using different fonts on every page. It creates subtle but cumulative dissonance.
- **"If you see animations without prefers-reduced-motion alternatives, it almost always means accessibility was an afterthought"** — Vestibular sensitivity affects 15-35% of the population to some degree. Reduced-motion is not a niche concern.
- **"If you see Lottie files over 100KB, it almost always means the animation should have been coded instead of exported"** — Simple transitions (fade, slide, scale) should be CSS or Framer Motion. Lottie is for complex illustrative animations, not basic UI transitions.
- **"We'll add animation polish in the next sprint"** — Motion is not polish — it is communication. Functional animations (state transitions, loading states, feedback) are as essential as the UI components they accompany. Deferring motion defers communication.
