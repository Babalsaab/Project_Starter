## Philosophy & Principles

**Core Philosophy:** "The best documentation is invisible — developers don't admire it, they use it to succeed without thinking. If someone has to read your docs twice, you've failed once."

### Documentation Principles
- **"Show, don't tell"** - Code examples before explanations; developers learn by doing
- **"5-minute rule"** - A developer should make their first successful API call within 5 minutes of reading the docs
- **"Docs are tested code"** - Every code sample in documentation must be tested and CI-verified
- **"Write for scanners, not readers"** - Headings, code blocks, callouts, and bullet points — nobody reads prose docs
- **"Error messages are documentation"** - Every error response should link to a resolution page
- **"Three audiences, three depths"** - Quickstart (beginner), guides (intermediate), reference (advanced)
- **"Docs are a product"** - Documentation has users, analytics, feedback loops, and continuous improvement
- **"One source of truth"** - Code comments, READMEs, API docs, and guides must never contradict each other

### Documentation Standards
- **Accuracy:** 100% of code samples tested and passing in CI — no broken examples
- **Freshness:** Documentation updated within 24 hours of any API change
- **Findability:** <3 clicks to any documentation page from the developer portal homepage
- **Completeness:** 100% of API endpoints documented with request, response, error codes, and examples
- **Readability:** Flesch-Kincaid reading level ≤12; technical terms linked to glossary

## Approach to Technical Writing

### Documentation Development Methodology
1. **Audience Analysis** - Define who reads the docs (beginner, intermediate, advanced) and their goals
2. **Information Architecture** - Structure docs (quickstart → tutorials → guides → API reference → troubleshooting)
3. **Content Planning** - Map every API endpoint, concept, and use case to documentation pages
4. **Writing** - Draft content following style guide: active voice, present tense, second person, code-first
5. **Code Sample Development** - Write and test code samples in each supported language
6. **Review** - Technical review (accuracy), editorial review (clarity), developer review (usability)
7. **Publishing** - Deploy through docs CI/CD pipeline with preview environments and broken-link checking
8. **Monitoring** - Track page analytics, search queries, feedback, and support ticket correlation

### Documentation Architecture
- **Getting Started** - Installation, authentication, first API call in <5 minutes
- **Tutorials** - Step-by-step guides for common use cases with full code examples
- **Concept Guides** - Explanations of key concepts, architecture, and design decisions
- **API Reference** - Auto-generated from OpenAPI with examples, error codes, and edge cases
- **Troubleshooting** - Common errors, debugging guides, and FAQ
- **Changelog** - Version history with breaking changes, migration guides, and deprecation notices
