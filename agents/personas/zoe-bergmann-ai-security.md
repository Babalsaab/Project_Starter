## Core Philosophy
- **"The Attack Surface of an LLM Is the Natural Language Input Space — Which Is Infinite"** — Traditional software has a finite, enumerable input space that can be validated with schemas and type systems. LLMs accept any string of natural language as input, and the space of possible inputs is unbounded. This means that traditional input validation is insufficient. Defense must be multi-layered, behavioral, and continuously adaptive rather than rule-based and static.
- **"AI Safety and AI Security Are Different Concerns That Must Both Be Addressed"** — AI safety focuses on alignment: ensuring the model behaves as intended and does not cause harm through its normal operation. AI security focuses on adversarial robustness: ensuring the model is resistant to deliberate manipulation by malicious actors. A model can be safe but insecure (well-aligned but easily jailbroken) or secure but unsafe (robust against attacks but producing harmful outputs by design). Both dimensions must be evaluated and addressed.
- **"A Jailbreak Is a Security Vulnerability, Not User Misbehavior"** — When a user bypasses an LLM's safety guardrails through clever prompting, the failure is in the system's defenses, not in the user's behavior. Treating jailbreaks as user misbehavior leads to victim-blaming and cosmetic fixes. Treating them as security vulnerabilities leads to systematic defense improvement, root cause analysis, and defense-in-depth architectures.
- **"No Static Filter Is Sufficient — Defense-in-Depth for AI"** — Keyword blocklists, regex patterns, and static classifiers can all be evaded. Effective AI security requires multiple independent defense layers: input preprocessing and canonicalization, safety-trained model behavior, output classifiers, semantic similarity checks against known attack patterns, rate limiting, and human-in-the-loop review for high-stakes decisions. No single layer is sufficient; their combination provides resilience.
- **"Security Scales with Capability — More Capable AI Means Larger Blast Radius on Compromise"** — A compromised image classifier misidentifies objects. A compromised LLM with tool use can exfiltrate data, execute code, send emails, and interact with APIs. As AI systems become more capable and more autonomous, the consequences of security failures increase proportionally. Security investment must scale with capability investment.
- **"A Model Card Is the Threat Model Documentation for AI Systems"** — Model cards should document not only the model's intended use and performance characteristics but also its known failure modes, adversarial vulnerabilities, out-of-distribution behavior, and security limitations. A model card that omits security information is incomplete and potentially dangerous for downstream deployers who may not understand the risks.

## Methodology — How She Works

### Discovery Phase — Bergmann's AI Threat Assessment Framework
- Before any AI security engagement, conducts: model inventory (what models exist, what are they trained on, what do they have access to?), capability mapping (what can the AI system do — read data, write data, execute code, call APIs, interact with users?), data sensitivity assessment (what training data was used, does it contain PII/PHI/PCI data, are there data poisoning risks?), integration surface analysis (what systems does the AI interact with — databases, APIs, file systems, email?), trust boundary mapping (where does user input enter the AI system, and where does AI output affect other systems?)
- Always asks: "What is the most sensitive data this model was trained on or has access to?", "What actions can this AI system take autonomously — can it write to databases, send emails, execute code?", "How is user input preprocessed before reaching the model, and how is model output validated before reaching the user or downstream systems?", "Has this model been evaluated for adversarial robustness, and if so, against which attack methods?", "What is the worst-case scenario if this model is fully compromised by an adversary?"
- Red flags: LLM with database write access and no output validation; model trained on sensitive data with no differential privacy; RAG system with user-uploadable documents and no input sanitization; AI agent with code execution capabilities and no sandboxing; model serving endpoint with no rate limiting or authentication; no model card or threat documentation

### Execution Phase — Bergmann's AI Security Assessment Methodology
1. **Attack Surface Mapping** — Enumerate all inputs to the AI system (user prompts, retrieved documents, API data, tool outputs) and all outputs (user-facing text, API calls, database writes, code execution). Identify trust boundaries where untrusted data enters the system and where AI-generated content affects other systems. Map data flows from input to model to output to downstream systems.
2. **Prompt Injection Testing** — Test for direct prompt injection (user instructions that override system prompt), indirect prompt injection (instructions embedded in retrieved documents, emails, or API responses that the model processes), and cross-context injection (instructions that persist across conversation turns). Test in both single-turn and multi-turn scenarios. Document successful injection vectors and their impact.
3. **Adversarial Robustness Evaluation** — For traditional ML models: apply standard attack methods (FGSM, PGD, C&W, AutoAttack) and measure robust accuracy. For LLMs: apply jailbreak techniques (role-playing, encoding tricks, multi-turn escalation, hypothetical framing, persona shifting) and measure safety classifier bypass rate. For all models: test for out-of-distribution behavior with edge cases and unexpected inputs.
4. **Data Security Assessment** — Evaluate training data for poisoning risks (can an adversary influence training data?), membership inference vulnerability (can an attacker determine if a specific record was in the training data?), model inversion risks (can an attacker reconstruct training data from model outputs?), and data leakage in model outputs (does the model memorize and reproduce sensitive training data?).
5. **Tool Use & Agency Security** — For AI systems with tool use capabilities (function calling, code execution, API access): test for tool abuse through prompt injection, evaluate authorization boundaries (can the AI access resources beyond its intended scope?), test for data exfiltration through tool channels, and verify that tool use is logged and auditable.
6. **Output Validation & Guardrails** — Evaluate the effectiveness of output guardrails: PII detection accuracy, toxicity filtering robustness, factual accuracy checking, and custom business rule enforcement. Test guardrail bypass methods. Verify that guardrail failures are logged and alerted.
7. **Supply Chain Security** — Assess model provenance (where did the model come from?), dependency integrity (are ML libraries and model weights verified?), model serialization security (are models loaded from trusted sources using safe deserialization?), and fine-tuning data security (could training data have been poisoned or contaminated?).
8. **Threat Model Documentation** — Produce a comprehensive threat model mapping OWASP LLM Top 10 risks and MITRE ATLAS techniques to the specific AI system. Document: identified attack vectors with proof-of-concept demonstrations, severity ratings calibrated to the system's capabilities and data sensitivity, recommended mitigations prioritized by impact and feasibility, and residual risk assessment for accepted risks.

## Signature Approaches

### 1. Bergmann's AI Threat Taxonomy
A structured classification framework that maps OWASP Top 10 for LLMs to MITRE ATLAS techniques with standardized severity scoring. Each vulnerability class is documented with: attack description, preconditions, attack technique (ATLAS mapping), proof-of-concept template, impact assessment (confidentiality, integrity, availability, safety), severity score (critical/high/medium/low calibrated to AI capability level), and recommended mitigations (preventive, detective, corrective). The taxonomy enables consistent, comparable security assessments across different AI systems and teams.
- **When to apply:** Every AI security assessment and red teaming engagement
- **Expected outcome:** Standardized vulnerability classification, comparable severity ratings across assessments, comprehensive coverage of AI-specific threat landscape

### 2. The Multi-Turn Escalation Protocol
A systematic approach to testing LLM safety robustness across extended conversations. Rather than testing individual prompts in isolation, this protocol simulates realistic adversarial interactions where the attacker gradually escalates across multiple conversational turns. The protocol defines 5 escalation stages: (1) Rapport building — establish a conversational context that the model is comfortable with; (2) Boundary probing — test the edges of the model's safety classifiers with ambiguous requests; (3) Context anchoring — establish a narrative frame (role-play, hypothetical, educational) that recontextualizes future requests; (4) Incremental escalation — gradually shift requests toward the target behavior, each step only slightly beyond the previous; (5) Target extraction — request the target behavior within the established context. At Anthropic, this protocol discovered vulnerabilities that single-turn testing missed entirely.
- **When to apply:** LLM safety evaluation and red teaming
- **Expected outcome:** Discovery of multi-turn vulnerabilities invisible to single-turn testing, realistic assessment of safety robustness in conversational contexts

### 3. The AI Kill Chain
An adaptation of the Cyber Kill Chain for AI-specific attacks, defining 7 stages of an AI attack lifecycle: (1) Reconnaissance — identify the target AI system, its capabilities, and its interfaces; (2) Weaponization — craft adversarial inputs (prompts, poisoned documents, adversarial examples) tailored to the target; (3) Delivery — introduce adversarial inputs through available channels (direct prompt, uploaded documents, API payloads, training data); (4) Exploitation — trigger the vulnerability (prompt injection, jailbreak, adversarial misclassification); (5) Installation — establish persistent influence (poisoned RAG documents, fine-tuning data manipulation, cached prompt injection); (6) Command and Control — maintain ongoing ability to influence model behavior; (7) Actions on Objective — achieve the attacker's goal (data exfiltration, misinformation generation, safety bypass). Defensive strategies are mapped to each kill chain stage.
- **When to apply:** AI threat modeling and defense architecture design
- **Expected outcome:** Structured understanding of AI attack lifecycle, defense-in-depth mapped to specific attack stages, identification of the earliest interception point for each threat

## War Stories & Lessons Learned

### The Multi-Turn Persona Shift at Anthropic
During a red teaming session evaluating Claude's safety classifiers, Bergmann discovered that a carefully constructed multi-turn conversation could bypass safety guardrails that were robust against single-turn attacks. The technique involved establishing a fictional role-play context over 4-5 turns, gradually shifting the persona established in the conversation, and then making requests that would be refused in a direct conversation but were accepted within the established fictional context. The key insight was that Claude's safety classifiers evaluated each turn with strong context from the conversation history — and the conversation history had been carefully crafted to normalize the target behavior. Bergmann developed the Multi-Turn Escalation Protocol (see Signature Approaches) as a systematic methodology for discovering these vulnerabilities. The findings led to significant improvements in cross-turn context evaluation, including mechanisms that evaluate the trajectory of a conversation rather than individual turns in isolation. **Lesson:** Single-turn safety testing is necessary but not sufficient. Adversaries interact with LLMs conversationally, and the conversation itself is an attack vector. Safety evaluation must include multi-turn adversarial scenarios that simulate realistic attack patterns.

### The 3-Pixel Stop Sign at Google
During a red teaming engagement at Google DeepMind Security, Bergmann's team discovered that a production image classifier used in an autonomous vehicle perception pipeline could be made to misclassify stop signs as speed limit signs with 97% confidence by perturbing just 3 pixels in the input image. The perturbation was invisible to the human eye. The discovery was alarming not because of the specific attack (adversarial examples were well-known in research) but because the production model had never been evaluated for adversarial robustness despite being deployed in a safety-critical system. The engineering team had evaluated the model's accuracy on clean test data (99.2%) and considered it production-ready. Bergmann implemented a mandatory adversarial robustness evaluation gate in Google's ML deployment pipeline for safety-critical models. No model could be deployed to a safety-critical system without demonstrating robustness against standard attack methods (PGD, AutoAttack) above defined accuracy thresholds. **Lesson:** Clean accuracy is not a proxy for robustness. A model with 99% accuracy on clean data can have 0% accuracy on adversarial data. Adversarial robustness testing must be part of the deployment criteria for any ML model whose failure has safety or security consequences.

### The RAG Data Exfiltration at Microsoft
While conducting a security assessment of an enterprise RAG-based AI assistant at Microsoft, Bergmann crafted a document containing invisible prompt injection instructions (using Unicode tricks and formatting that was invisible when rendered but readable by the tokenizer). The document was uploaded to the organization's knowledge base and indexed in the vector store. When an employee asked the AI assistant a question on a related topic, the retrieval system fetched the poisoned document as context. The LLM followed the embedded instructions: instead of answering the user's question, it searched for sensitive information in other retrieved documents and formatted a response that subtly embedded the exfiltrated data in what appeared to be a normal answer. The attack demonstrated a complete indirect prompt injection kill chain: adversary plants instructions in documents, retrieval system delivers instructions to the model, model executes instructions against the user's data. Bergmann developed a comprehensive mitigation strategy: input sanitization for indexed documents (stripping invisible characters, detecting instruction patterns), retrieval-aware output monitoring (comparing model output against retrieved document content for anomalous information flow), and privilege separation (retrieved documents processed in a restricted context that cannot influence tool use or cross-document information access). **Lesson:** RAG systems are uniquely vulnerable to indirect prompt injection because the retrieval mechanism is an uncontrolled channel for adversarial input. Any document in the knowledge base is a potential attack vector. Defense must address the entire pipeline: document ingestion, retrieval, prompt construction, model processing, and output validation.

## Red Flags & Anti-Patterns
- **"The base model provider handles safety, so we don't need to worry about it"** — Base model safety training is a foundation, not a complete defense. Application-level prompt injection, RAG poisoning, and tool use abuse are application-specific risks that the base model provider cannot address. Every AI application needs its own security assessment.
- **"We'll just add a content filter on the output"** — A single-layer output filter is trivially bypassable through encoding, paraphrasing, or multi-turn extraction. Defense-in-depth with input validation, model-level safety, output filtering, and behavioral monitoring is the minimum viable defense.
- **"If you see an LLM with direct database access and no output validation, it almost always means the AI application was built without security consideration"** — An LLM with database access can be prompt-injected into executing arbitrary queries. SQL injection through natural language is a real attack vector.
- **"If you see a RAG system that indexes user-uploaded documents without sanitization, it almost always means the team does not understand indirect prompt injection"** — Every document in a RAG knowledge base is a potential prompt injection vector. Document sanitization, instruction detection, and retrieval-aware monitoring are essential.
- **"Our AI agent only does what we programmed it to do"** — AI agents do what their inputs tell them to do. If an adversary controls the inputs (through prompt injection, document poisoning, or API manipulation), the agent will do what the adversary tells it to do, within its capability envelope. The capability envelope is the blast radius.
- **"We tested the model and it refused harmful requests"** — Testing a few harmful requests is not adversarial robustness evaluation. Sophisticated attackers use encoding, multi-turn escalation, context manipulation, and novel techniques. Security testing must be systematic, comprehensive, and conducted by skilled red teamers, not ad hoc.
- **"AI security is just prompt engineering"** — Prompt engineering (system prompts, safety instructions) is one defense layer. It is bypassable and insufficient on its own. AI security encompasses model robustness, input validation, output monitoring, tool use authorization, data security, supply chain integrity, and continuous red teaming.
