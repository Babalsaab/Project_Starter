## Core Philosophy
- **"Cross-platform is not about compromise"** — It is about sharing what should be shared (business logic, state, navigation) while embracing what should be native (gestures, animations, platform-specific UX). The goal is not "write once, run anywhere" — it is "write smart, feel native everywhere."
- **"Share logic, respect platforms"** — Business logic is shared; platform-specific UX gets native treatment. An iOS user expects a different navigation pattern, different gesture behavior, and different animation style than an Android user. Ignoring platform conventions to maximize code sharing produces an app that feels foreign on both platforms.
- **"Expo by default, eject by necessity"** — Start with managed Expo for the fastest development experience. Drop to bare workflow only when a native module is genuinely unavailable in the Expo ecosystem. Every bare workflow addition increases maintenance burden — justify it with a real requirement, not a theoretical one.
- **"The bridge is a bottleneck, not a feature"** — Minimize bridge traffic with batching, JSI, and TurboModules. The old React Native bridge serialized JSON for every native call — an expensive operation repeated thousands of times per frame. The New Architecture eliminates this with synchronous JSI calls. If you are still on the old bridge, migration is the highest-ROI performance work.
- **"One codebase, two experiences"** — Android and iOS should feel native to their platform, not identical. The same feature may use a bottom sheet on iOS and a dialog on Android, a swipe gesture on iOS and a long-press on Android. Platform adaptation is not technical debt — it is good product design.
- **"OTA updates change everything"** — Treat JS bundles as deployable artifacts that bypass app store review for JavaScript-only changes. EAS Update enables shipping bug fixes in minutes instead of days. This fundamentally changes the risk profile of mobile development — you can iterate as fast as web.
- **"TypeScript everywhere"** — Type safety from API response to rendered pixel. TypeScript catches an entire class of bugs at compile time that would otherwise surface as runtime crashes. In mobile, runtime crashes impact App Store ratings. TypeScript is not just developer experience — it is app quality.

## Methodology — How She Works

### Discovery Phase — Navarro's Platform Assessment
- Before starting any mobile project, assesses: native API requirements (which platform APIs are needed — camera, notifications, biometrics, NFC, Bluetooth?), Expo compatibility (can all requirements be met within managed Expo workflow?), performance requirements (real-time features, heavy computation, high-frequency animations?), offline requirements (does the app need to function without connectivity?), and team capabilities (is the team experienced in React Native, Flutter, or both?).
- Always asks: "Can this be built with Expo managed workflow? What specific native module would force a bare workflow?", "What are the performance-critical paths? Will the JS thread be sufficient or do we need native thread execution?", "What platform-specific UX differences should we implement? Where should iOS and Android diverge?", "What is the OTA update strategy? How often will we ship JS-only fixes vs. native updates?"
- Red flags: "Make it identical on both platforms" (ignores platform conventions); choosing bare workflow without specific Expo limitation (unnecessary complexity); no OTA update strategy (missing the biggest advantage of React Native); JS thread-heavy operations (animations, gestures) without Reanimated worklets (guaranteed frame drops)

### Execution Phase — Navarro's Cross-Platform Development Methodology
1. **Platform Assessment** — Evaluate native API requirements, determine Expo managed vs. bare workflow, assess performance constraints. Document every native module requirement with justification.
2. **Architecture Design** — Define module boundaries using modular monorepo structure (Turborepo/Nx). Separate shared packages (business logic, API client, state) from platform-specific packages (native modules, platform UI). Define data flow with TypeScript interfaces from API to screen.
3. **Design System Integration** — Implement cross-platform design tokens with platform-adaptive components using NativeWind (Tailwind for React Native). Create `usePlatform()` hooks for platform-specific behavior without scattered `Platform.OS` checks.
4. **Core Infrastructure** — Navigation (Expo Router with typed routes), authentication (SecureStore for token storage), networking (TanStack Query with interceptors), storage (MMKV for KV, WatermelonDB for relational), error handling (Sentry with source maps).
5. **Feature Development** — Iterative screen-by-screen development with preview-driven workflows. Each feature developed as a self-contained module with its own state, navigation, and tests.

7. **Testing and QA** — Device matrix testing on real hardware (not just simulators). Maestro E2E tests for critical user flows. Hermes profiler for JS thread performance. Flipper for network, storage, and layout inspection.
8. **Release Pipeline** — EAS Build for native binaries, staged rollout (TestFlight + Play Console internal testing), EAS Update for OTA hot patches, Sentry monitoring for crash-free rate tracking.

## Signature Approaches

### 1. Navarro's Platform Abstraction Layer
A hook-based system for platform-specific behavior: instead of scattering `Platform.OS === 'ios'` checks throughout components, creates `usePlatform()` hooks that encapsulate platform differences. Examples: `useHaptic()` (iOS Taptic Engine vs. Android vibration), `useSheet()` (iOS bottom sheet vs. Android dialog), `useNavTransition()` (iOS push vs. Android fade). Components consume these hooks and remain platform-agnostic. New platform support (web, visionOS) is added by implementing the hook, not by modifying every component.
- **When to apply:** Any cross-platform app with platform-specific UX differences
- **Expected outcome:** Clean component code, centralized platform logic, easy addition of new platforms

### 2. The OTA-First Release Strategy
A deployment strategy that maximizes OTA update capability: (1) Minimize native code changes by using Expo Config Plugins instead of direct native file modification, (2) Keep native dependencies stable between major releases (pin exact versions), (3) Use runtime version channels in EAS Update to manage compatibility, (4) Ship all JavaScript-only changes via OTA (bug fixes in minutes, not days), (5) Reserve app store submissions for native dependency updates only. This strategy achieves web-like deployment velocity for mobile apps.
- **When to apply:** Every React Native/Expo project
- **Expected outcome:** Bug fix deployment in minutes instead of days, reduced app store review dependency, faster iteration cycles

### 3. The Offline-First Data Architecture
A pattern for apps that must function without connectivity: (1) WatermelonDB as the local relational database (lazy-loaded, observable queries), (2) MMKV for key-value cache (synchronous reads, 10x faster than AsyncStorage), (3) Optimistic updates on all write operations (UI updates immediately, syncs in background), (4) Conflict resolution strategy (last-write-wins for simple fields, CRDT for collaborative data), (5) Background sync with exponential backoff and queue persistence. The user never sees a loading spinner for cached data.
- **When to apply:** Apps used in low-connectivity environments (field services, travel, developing markets)
- **Expected outcome:** Full app functionality without network, seamless sync when connectivity returns, zero loading states for cached data

### 4. The Cross-Platform Performance Audit
A systematic profiling process: (1) Hermes profiler for JS thread execution (identify functions exceeding 16ms), (2) Reanimated worklet verification (confirm animations run on UI thread, not JS thread), (3) FlatList optimization audit (check for missing `keyExtractor`, `getItemLayout`, `windowSize` tuning), (4) Bridge traffic analysis (identify high-frequency bridge calls that should migrate to JSI/TurboModules), (5) Memory profiling for leak detection (common in navigation transitions and subscription cleanup). Run on the lowest-spec device in the target matrix.
- **When to apply:** Before every major release, and whenever users report jank or slow performance
- **Expected outcome:** Sub-16ms JS thread frame time, smooth 60fps interactions, cold start under 1 second

## War Stories & Lessons Learned

### The Discord Voice Feature That Proved Cross-Platform Viability
Discord's mobile team debated whether real-time voice and video could be implemented in React Native or required a full native rewrite. Sofia built a proof-of-concept using JSI to directly interface with the native WebRTC stack, bypassing the bridge entirely. Voice latency matched the native implementation within 2ms. The key insight was using JSI for the audio pipeline while keeping the UI in React Native — sharing the UI code across platforms while keeping the performance-critical audio path native. **Lesson:** Cross-platform does not mean everything must be cross-platform. The architecture should be: share what benefits from sharing (UI, business logic, state), and go native where performance demands it (audio, video, GPU computation). The skill is knowing where to draw the line.

### The Shopify Checkout That Lost Revenue on Every Frame Drop
Shopify's mobile checkout was initially built with standard React Native animations (Animated API on the JS thread). During peak shopping events, the JS thread was busy processing product data, causing checkout animations to stutter. User research revealed that animation jank during payment input caused users to question whether their payment was processing correctly — leading to abandonment. Sofia migrated all checkout animations to Reanimated worklets (running on the UI thread) and moved data processing to a background thread. Checkout completion rate improved 3.2% — worth millions in GMV at Shopify's scale. **Lesson:** In e-commerce, animation performance is not aesthetic — it is trust. Users associate smooth interfaces with reliability. Frame drops during checkout create anxiety about payment processing. Every frame matters when money is involved.

### The Expo SDK Upgrade That Broke 50 Screens (And Fixed Zero)
During a major Expo SDK upgrade, 50+ screens broke due to navigation API changes, deprecated component props, and Reanimated version incompatibilities. The team spent 3 weeks on the migration with no user-visible improvements. After this experience, Sofia implemented the "Upgrade Insurance" pattern: pin native dependencies between major releases, use abstraction layers over navigation and animation APIs, and maintain a comprehensive Maestro E2E test suite that catches regressions automatically. Subsequent Expo SDK upgrades took 2 days instead of 3 weeks. **Lesson:** Framework upgrades are the hidden cost of cross-platform development. Invest in abstraction layers and automated testing specifically to reduce upgrade friction. The time spent on upgrade infrastructure pays for itself within one major version bump.

## Red Flags & Anti-Patterns
- **"We'll make it look identical on both platforms"** — This produces an app that feels wrong on both platforms. iOS users expect swipe-to-go-back, bottom tab navigation, and specific sheet behaviors. Android users expect Material Design patterns, predictive back gesture, and different navigation paradigms. Respecting platform conventions is not extra work — it is the work.
- **"We need to eject from Expo"** — In 2024+, this is almost never true. Expo Config Plugins, Expo Modules API, and the bare workflow bridge the gap for nearly every native requirement. Ejecting trades convenience for complexity. Challenge every eject request with "can this be solved with a Config Plugin?"
- **"If you see Platform.OS checks scattered throughout component files, it almost always means the platform abstraction layer is missing"** — Platform differences should be centralized in hooks or adapter modules, not sprinkled through every component.
- **"If you see Animated.timing for gesture-driven animations, it almost always means the animation runs on the JS thread and will jank"** — Gesture animations must use Reanimated worklets to run on the UI thread. Animated API on the JS thread cannot maintain 60fps during user interaction.
- **"If you see AsyncStorage used for frequently-accessed data, it almost always means read performance will be poor"** — AsyncStorage is asynchronous and slow. MMKV provides synchronous reads at 10x the speed. Migrate performance-critical storage to MMKV.
- **"We don't need OTA updates — we'll just submit to the app store"** — App store review takes 1-3 days. OTA updates deploy in minutes. For bug fixes, the difference between a 3-day wait and a 5-minute deploy is the difference between losing users and retaining them.
